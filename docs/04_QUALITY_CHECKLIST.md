# 品質確認チェックリスト

この文書は、原画への文字合成を中心としたLINEスタンプ制作の確認手順です。確認日：2026-11-11。

**このリポジトリには、現物の原画・制作済みスタンプ・実機での確認結果はまだ含まれていません。以下は今後の制作で使う基準と記録方法です。** 文書を読んだだけで、作品の確認が完了したことにはしません。

制作の流れは [制作手順](03_PRODUCTION_WORKFLOW.md)、対象種類ごとの規格は [調査・出典](01_RESEARCH_AND_SOURCES.md)、実際の判定記録は [REVIEW_LOG](../templates/REVIEW_LOG.md) を参照してください。

## 1. 判定と完了の扱い

| 判定 | 意味 | 次にすること |
|---|---|---|
| PASS | 対象の版について、必要な方法で確認し、基準を満たした | 確認方法と証跡を残す |
| 要修正 | 具体的な問題を確認した | 影響する部分を修正し、その部分と周辺を再確認する |
| 未確認 | 必要な確認をまだ実施できていない | 理由と解消方法を記録し、独立して進められる作業は続ける |
| 対象外 | 今回の制作範囲に該当しない | 対象外とした理由を記録する |

- 初期状態は「未確認」。チェック欄を埋めるためにPASSにしない。
- 「たぶん読める」「スクリプトが正常終了した」は、画像を見た証拠にならない。
- 適用される必須項目に「要修正」「未確認」が残る場合、完成品として扱わず、どこまで確認できた試作・候補なのかを明記する。
- 環境不足で一部を確認できなくても、企画・候補作成・技術検査など他の作業は進める。実LINEプレビューだけ未確認なら、その項目を残して内部検証の結果を報告する。
- 未確認をすべてユーザーへの質問にしない。既存の指示・素材・環境確認で解消できることを先に進め、意図の確認が不可欠な点だけをまとめる。
- 必須確認は今回の依頼範囲と出力に必要なもの。実LINEプレビューが利用できない場合は、その状況を明記して、内部確認を終えたPNGや一覧を引き渡せる。

## 2. 何を自動で確認できるか

| 確認方法 | 主に分かること | それだけでは分からないこと |
|---|---|---|
| ファイル・数値の検査 | 形式、寸法、容量、色モード、ファイル数、アルファ値、文字列や設定値 | 読みやすさ、キャラらしさ、透過処理の自然さ |
| 描画範囲・レイヤーの検査 | 実描画の境界、画面外へのはみ出し候補、指定領域との重なり候補 | 重なりが表現として適切か、顔や仕草の意味が失われていないか |
| OCR・類似度などの補助検査 | 誤字・欠落・似た構図の疑いがある画像の抽出 | 文言の完全一致、濁点等の正確さ、重複の許容可否 |
| 出力画像の目視確認 | 文字の形、表情、色、隙間、縮小時の見え方、背景との関係 | ユーザーが望む口調・作風・許可範囲の確定 |
| ユーザーの指示・採用履歴との照合 | 文言、原画の変更範囲、用途、採用基準への適合 | 指示されていない好みの断定 |

画像を確認できるAIを利用する場合も、実際に該当版の画像を見たときだけ画像確認として記録します。OCR結果だけを画像確認の代わりにしません。

## 3. 入力と制作範囲

| ID | 確認すること | 方法・判断のポイント |
|---|---|---|
| I-01 | スタンプの種類と対象セットが明確 | 通常の静止画、アニメーション、メッセージ等を区別。別種類の規格を流用しない |
| I-02 | 原画・文言・採用済みの方針が特定できる | ファイル名、版、文言の原本、指示を [STAMP_PLAN](../templates/STAMP_PLAN.md) に対応づける |
| I-03 | 原画の変更範囲が明確 | 標準は原画への文字合成。等比拡縮・配置、新表情、反転、切り抜き変更など、許可された範囲を区別する |
| I-04 | 比較と修正の範囲が決まっている | 候補数、比較する違い、生成・作業予算、修正回数の目安を記録。未指定なら合理的な試作範囲を仮置きして進め、有料処理は既に認められた範囲で行う |
| I-05 | 素材・書体の利用条件を確認した | 使用する原画、フォント、追加素材の配布元や条件を記録。不明なら確認済みと扱わない |

## 4. 技術的に検査できる項目

数値は対象種類の現行公式ガイドラインを参照します。ここで独自の最大寸法や固定余白を追加しません。

| ID | 確認すること | 証跡の例・限界 |
|---|---|---|
| T-01 | 形式・縦横寸法・容量・色モード・個数が対象規格に適合 | 対象版のファイル一覧と検査結果。メイン画像、タブ画像、スタンプ本体を分ける |
| T-02 | 必要な透過がデータ上存在する | アルファチャンネルと値を確認。アルファがあるだけでは、不要背景が消えているとは判定しない |
| T-03 | 合成に渡した文言が指定原文と一致 | 文言原本と入力文字列を照合。改行等の組版上の変更を区別する。これだけでは出力された字形の正しさは保証しない |
| T-04 | 使用した書体が必要な日本語・記号を描画できる | 使用文字の対応状況、意図しない代替書体や欠けた字の有無。最終出力も画像で確認する |
| T-05 | 実描画範囲が収まっている | フォントサイズやテキスト枠ではなく、縁取り・装飾を含む描画後の境界（bbox）を見る。影や薄いピクセルの扱いも確認する |
| T-06 | 不要な外周余白・孤立ピクセルを検出できる | アルファの境界を調べ、現在の公式規格と照合する。薄い線や意図した装飾を不要と決めつけない |
| T-07 | 原画と出力の対応・変更履歴を残した | 元画像の保存、使用版、等比拡縮・配置の記録。元ファイルの一致だけでは合成後の見え方を保証しない |
| T-08 | 編集途中の版と採用版が混在していない | ID、候補、版、採否を一覧で照合する。再出力した版は古い検査結果をそのまま引き継がない |

自動検査が利用できない項目は、同じ内容を確認できる別の方法を記録します。検査スクリプトの導入自体を制作の目的にしません。

## 5. 出力画像を見て確認する項目

| ID | 確認すること | 見るポイント |
|---|---|---|
| V-01 | 誤字・欠字・重複字・別字がない | 原文と一文字ずつ照合。「っ」「ゃ」「ゅ」「ょ」、濁点・半濁点、長音、句読点も見る |
| V-02 | 小さく表示しても読める | 漢字の内部、小さな文字、細い線、濁点が潰れていない。太い縁取りで文字同士がつながっていない |
| V-03 | 文字の端や装飾が切れていない | 上下左右、縁取り、弧状・斜め配置、改行末尾。bboxの数値検査と併用する |
| V-04 | 原画の特徴が保たれている | 顔・体型・線・色・衣装・固有の特徴を元画像と比較。等比拡縮による自然な変化と、意図しない描き直しを分ける |
| V-05 | 顔や重要な仕草が読める | 目、口、手、持ち物、ポーズの意味を文字で隠していない。重なりがあっても、表現として適切かを画像で判断する |
| V-06 | 文字とキャラの大きさ・距離が適切 | 空間があるのに文字が小さすぎない。意味のない大きな隙間、窮屈な接触、視線が迷う配置がない |
| V-07 | 改行・読み順・強調が自然 | 単語途中の不自然な分断、複数の読み順、強調しすぎ、文字の横潰れがない |
| V-08 | 背景を変えても意味が伝わる | 明るい背景、暗い背景、色付き背景で確認。黒い文字や白い装飾、淡い輪郭が消えないかを見る |
| V-09 | 透過の仕上がりが自然 | 白い板、疑似的な市松模様、切り抜き残り、不自然な白縁、半透明の汚れがない |
| V-10 | 言葉と表情・ポーズが合っている | 喜び・謝罪・遠慮などの感情と強さが矛盾しない。わざとずらす表現なら採用理由を記録する |
| V-11 | セットの中で区別しやすい | 同じ位置・同じ大きさ・同じ外形の反復に偏っていない。類似度の数値だけで重複と判断しない |
| V-12 | セットとしてまとまっている | キャラの同一性、文字の雰囲気、線、色の関係が保たれ、変化がランダムな色替えだけになっていない |

### 縮小と実LINEプレビュー

- 原寸と、例えば50%・25%に縮小した画像を並べる方法は、内部で弱点を探すための試験例です。LINEの実際の表示サイズが常にその値になるという意味ではありません。
- 一覧では「選ぶときに区別しやすいか」、トーク相当の表示では「送った意味がすぐ伝わるか」を確認します。
- 利用できる場合は実際のLINE側のプレビューでも確認し、使用した機能、端末・表示環境、確認日、画像の版、スクリーンショット等を記録します。
- 自作の背景合成やモック画面は「内部プレビュー」と記し、「LINE実機確認済み」と呼びません。
- 実プレビューの証跡に私的な会話やアカウント情報が写る場合は、作品の確認に必要な範囲だけを残します。

## 6. 意図と採用の確認

| ID | 確認すること | 判断の根拠 |
|---|---|---|
| D-01 | 送りたい相手・場面・口調に合う | ユーザーの指示とセットの企画。未指定なら仮定を記し、販売実績や好みを捏造しない |
| D-02 | 候補の違いが比較に役立つ | 読みやすさ重視、表情重視、一体感重視など、違いを短く説明できる |
| D-03 | 採用理由と不採用理由が具体的 | 「高品質」「かわいい」だけでなく、文字が読みやすい、仕草が残る、他と区別できる等を記す |
| D-04 | 好みの未確定事項を誤って確定していない | AIが候補を選んだことと、ユーザーが採用したことを区別。ユーザー確認が必要なのは重要な意図が未確定のときだけ |
| D-05 | 予算内で必要な比較を終えた | 候補数や修正回数を確認。上限に達したら現時点の最良案と残る問題を示し、無制限に再生成しない |

## 7. 修正と引き渡し

1. **問題を特定する。** 対象ID、版、問題の場所、原因の仮説を記録する。
2. **必要な部分を直す。** 文字サイズ、改行、位置、縁取り等の局所修正を優先する。キャラを直す必要がなければ描き直さない。
3. **周辺への影響を見る。** 文字を大きくしたなら、文字切れ、顔との重なり、全体のバランスを再確認する。
4. **新しい版で判定する。** 以前の採用版を残し、新しいファイルに対応する結果を記録する。単純な修正で全候補を作り直さない。
5. **確認範囲を添えて渡す。** 採用案、採用理由、確認した項目、要修正・未確認の項目、次の行動を短く報告する。

### 完了前の確認

- [ ] 採用版と、判定・証跡の版が一致している。
- [ ] 原画・指定文言・許可された変更範囲を守っている。
- [ ] 技術検査と画像確認の両方を、実施した方法どおりに記録している。
- [ ] セット一覧、縮小、複数背景を確認した。
- [ ] 実LINEプレビューの実施状況を、内部プレビューと区別している。
- [ ] 要修正・未確認を隠さず、完成・試作・候補のどれかを正しく表記している。
- [ ] [REVIEW_LOG](../templates/REVIEW_LOG.md) に採用理由と次回に使えるルールを残した。
